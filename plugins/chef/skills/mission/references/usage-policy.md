# 파견과 사용량

## 역할과 입력

역할·모델·effort·도구·상속 정책은 현재 런타임 진입점의 실행 계약을 따른다. 지정한 설정을 확인할 수 없으면 미확인으로 보고한다.
문서 변경이 문구·양식이나 한 파일의 몇 절에 그치고 규칙의 뜻과 승인 범위가 그대로면 첫 리뷰도 작은 리뷰 역할로 하고, 변경 전 본 대비 diff를 넘긴다. 새 규칙·규칙 관계 변경과 질문·보고의 첫 리뷰는 심층 리뷰다.
공통 계약·구조 변경·원인 불명·판단 충돌, 작은 리뷰어가 돌려준 뜻·승인 범위 변경이면 근거와 남은 범위를 반환하고 심층 리뷰로 확대한다. 테스트 실행자는 원인 분석·모델 전환을 직접 하지 않는다.

코디네이터는 방향·최신 답·승인 원문·적용 규칙·양식의 실제 경로를 정하고
`reference snapshot --source <자료> --source <자료> --output <묶음.json>`으로 고정한다.
기존 묶음을 갱신할 때는 직전 snapshot 응답의 `output.sha256`을 `--expect-sha256 <해시>`로 넘긴다.
현재 파일 해시가 다르거나 출력이 참조 묶음이 아니면 덮어쓰지 않는다.
`reference check --input <묶음.json>`이 통과한 묶음 하나를 구현·수정·첫 리뷰·재리뷰 브리프가 모두 가리킨다.
재리뷰 입력은 그 묶음과 바뀐 절만이다. `brief <단위> --references <묶음.json>`의 출력에 작업별 계약·직전 finding·반환 항목을 더한다.
`reference show --input <묶음.json>`은 경로·해시·선택 메타데이터를 출력하며 원문 내용은 복사하지 않는다.
`--revision`·`--section`으로 자료의 개정·절을 덧붙일 수 있다. snapshot 출력은 프로젝트 안 상대 경로,
source는 명시한 외부 파일도 허용한다. 파일 해시는 의미·승인을 판정하지 않는다.
참조가 바뀌거나 충돌하면 코디네이터가 원문과 승인 범위를 확인해 묶음을 함께 갱신한다.
전체 대화·완료한 작업·큰 로그와 구현자 맥락을 리뷰어에게 fork하지 않는다.
프로젝트 자료는 프로젝트에서 참조하며 플러그인에 복사·요약·익명화하지 않는다.
프로젝트 판정이 가능한 규칙은 어댑터 검사 또는 `verify.commands[]`에 연결한다. 이 공개 플러그인에는 회사·고객·비공개 프로젝트의 규칙이나 사례를 어떤 형태로도 넣지 않으며, 예시는 처음부터 가상으로 만든다.

구현·검증처럼 비용이 큰 파견 전에 코디네이터는 실제 대상 경로, 파일·자원 소유와 허용된 편집 범위,
문서에 정의된 명령·API 사용법, 변경 파일·계약을 덮는 검증 명령을 확인하고 구체적 근거를 브리프에 넣는다.
확인에는 찾을 수 있는 자료를 한정해 조회한다. 경로·문법·검증을 만들어내지 않는다.

첫 구현의 구현자는 반환 전에 변경한 함수·블록 전체 또는 문서 전체를 확정 명세·승인·규칙·양식과 대조하고
명확한 결함과 명시적 규칙 위반을 모두 고친다. 지적 수정 라운드는 이번에 바뀐 줄과 그 줄이 닿는 호출부만 대조한다.
반환에는 대조 범위, 적용 자료의 실제 경로·절, 실행한 기계 검사와 결과, 미확인·제외 범위와 이유를 간결히 적는다. 일부만 대조했다면 전체 준수처럼 보고하지 않는다. 자기 확인은 기계적 준수 증명이나 독립 리뷰·clean 판정을 대신하지 않는다.
관련된 승인 수정은 같은 구현자에게 이어 맡길 수 있다. PoC 원본 스킬이 새 에이전트를 요구하면 그 계약을 따른다.
독립 리뷰어는 구현자로 바꾸지 않는다.

첫 리뷰는 확정 참조 묶음으로 전체 변경의 결함·명시적 규칙 위반·계약·호출부를 한 번에 대조한다. 문서도 의미·보존·문체를 한 번에 검토한다.
읽지 못한 경로는 검증 공백으로 적고 코디네이터가 같은 라운드 안에서 보강 지시한다.
finding에는 고정 id·`severity`·원인·근거를 붙이고 개선 제안은 별도로 둔다. 새 규칙을 만들어 지적하지 않는다.
열린 지적 0건(미해결 포함)에 제안만 남으면 clean이다. 제안은 루프 안에서 적용하지 않고 보고에 후속 후보로 남긴다.
재리뷰는 `review-scope`가 주는 파일별 diff(최신 리뷰 기록의 사본 기준, `review-start`를 썼으면 그 시작 시점 사본 대비, 새 파일 포함)·직전 finding·영향받는 계약과 호출자를 본다.
기준 스냅샷·근거가 무효하거나 영향 범위를 특정할 수 없으면 범위를 확대한다.
바뀌지 않은 부분은 실제 결함·규칙·원문 근거가 있는 Medium 이상일 때만 다시 열고 Low는 제안으로 돌린다.
이전 해소 근거를 대조하고 미해결·새 지적·회귀를 구분한다. 같은 소유·원인·참조 규칙의 수정은 묶어서 담당 작성자에게 돌린다.
열린 지적이 전부 Low이고 회귀가 아니며 수정이 지적한 줄 범위 안에서 시그니처·계약·공개 동작을 바꾸지 않으면
새 리뷰어 없이 코디네이터가 diff를 확인해 `closed-low`로 닫는다. 조건과 연속 제한은 `verification-workflow.md`를 따른다.
clean·findings·closed-low 모두 기록해야 다음 범위 비교가 직전 리뷰를 기준으로 한다.
리뷰 전 기계 검사·`review-start` 기록·수정 뒤 재검증 범위도 `verification-workflow.md`의 한 단위의 흐름을 따른다.
최종 통합 검증과 단위 사이 연결·공유 계약·미검토 변경 리뷰는 유지하며 리뷰 상한은 2라운드다.

동일 소유·검증을 공유하는 작은 수정은 묶어 파견한다. 기존 승인 단위를 자동 병합하거나 receipt를 공유하지 않는다.
문서 기존 답·설계 표 보존은 `check_human_doc.py --source`, JSON 구문·링크·상태 검사는 기존 CLI로 먼저 검사한다.
코디네이터는 생성 문서의 JSON 정본과 작성 담당 하나를 유지하고, 검토한 초안만 발행한다.
계획·receipt를 먼저 훑을 때는 `python "<mission-state>" <mission-state-runtime> inspect --plan <계획.json>` 또는 `... inspect --receipt <receipt.json>`을 쓴다. 둘 중 하나만 지정하며 mission·adapter·ACTIVE 없이 읽기 전용으로 요약한다. `source`, `identity`, `counts`, 단계별 `steps`·`statusCounts`, `failedSteps`, `failure.repeatCount`, `executionCounts`, `recorded` 포인터 중 필요한 부분만 확인한다. 원본 JSON·로그 전체를 컨텍스트에 싣지 않는다. `current_validity`는 `not_checked`이며, 이 요약은 현재 입력·정책·환경 검증이나 결과 재사용 판정이 아니다. 그 판정은 기존 `preflight`·`verify`가 맡는다.
반환 상세와 증거는 파일로 받고 `handoff <단위> --summary <짧은 결과> --detail <상세> --evidence <근거>`로 연결한다.
상세·증거는 프로젝트 안 기존 파일이며 `--evidence`를 반복할 수 있다. 기본 summary 상한은 1000자다.
`handoff`는 파일 포인터를 출력할 뿐 상태를 쓰거나 완료·승인을 판정하지 않는다.
채팅에는 결과·다음 일·미확인만 남긴다.
기계 검사만으로 의미 검토를 통과시키지 않는다. 취소·중단 상태만 보고 이미 도착한 같은 task 결과를 버리지 않는다. 재파견 전에 최종 본문·근거 파일·실제 완료 범위·입력 상태를 확인하고, 현재 입력에 유효한 결과는 재사용하며 미완료 범위만 후속 파견한다. 결과가 없거나 현재 입력에서 무효하면 다시 실행한다. `cancelled`는 clean을 뜻하지 않는다. 동일 입력·계획·환경의 검증 결과는 기존 `verify`가 검증해 재사용한다.

리뷰 3라운드에서 남은 것이 Low뿐이면 코디네이터가 `closed-low`로 닫는다. closed-low 조건이 안 되면 독립 재리뷰를 하거나 사용자에게 묻는다.
Medium 이상이 남았거나 수정끼리 충돌하거나 같은 지적이 재발할 때와 timebox 상한에서는
미해결 원인, 누락·충돌 참조, 회귀, 남은 판단과 수정·검증 범위를 진단해 멈춤 질문에 담는다. 같은 일을 더 돌리겠다는 연장 요청으로 대신하지 않으며 품질·검증 범위를 낮추지 않는다.

## 측정

실제 런타임이 제공하는 로그·모델·effort 증거를 기록하고 미확인 한계를 구분한다. Claude JSONL 측정은 [Claude 사용량](claude-usage.md)을 따른다. 다른 런타임 로그에 이 집계기를 적용하지 않는다.
