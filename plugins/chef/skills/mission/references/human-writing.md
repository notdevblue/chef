# 사람에게 공유할 문서

원문과 아래의 해당 양식·완성 예시로 쓴다. 핵심만 짧고 간결하게 요약하고, 예시는 문체와 순서만 참고한다. 예시의 사실이나 선택지는 가져오지 않는다.
모든 케이스를 읽거나 양식의 빈 절을 전부 채울 필요는 없다.

## 이번 문서에 맞는 자료

| 문서 | 양식 | 완성 예시 |
| --- | --- | --- |
| 범위·방향을 묻는 질문, 확인 B·C, 멈춤 질문 | [질문](confirm-template.md) | [독서 목록 범위 질문](examples/question.md) |
| 스키마·통신 구조를 승인받는 확인 A | [설계 승인](templates/design-confirm.md) | [독서 상태 저장·변경 설계](examples/design-confirm.md) |
| 결과와 다음 일을 알리는 보고 | [보고](templates/report.md) | [우편 구현 보고](examples/report.md) |

설계 승인에 대한 질문이면 설계 승인 자료를 고른다. 보고서에서 이미 다른 확인 문서가 묻는 선택은 결과와 영향을 짧게 알리고
그 문서로 연결한다. 확인 C의 피드백 반영 후보는 distill 결과가 있을 때만 질문으로 붙인다.

## 보존할 것

- 질문 id·번호·선택지의 의미·사용자 답·상태와 승인 범위를 바꾸지 않는다. 담당자·선행 조건·확인 시점·실패 결과도 판단의 일부다. 끝난 답은 다시 묻지 않는다.
- 서두에는 현재 목적·결정할 것 또는 결과만 쓴다. 과거 상태·철회·정정·수정 이유·문서를 어떻게 정리했는지는 공유 본문과 현재 상세에 쓰지 않는다. 유효하지 않은 설계는 현재 승인 대상으로 남기지 않는다.
- 질문에는 선택·이유·판단에 필요한 영향을, 설계 절에는 정확한 계약을, 범위 절에는 적용 대상·제외 조건을 둔다. 질문 정본은 정형 선택지와 짧은 근거를 중심으로 쓴다. 같은 동작·수치·제약·위험·승인 경계를 여러 절에서 다시 풀어 쓰지 않는다.
- 질문 선택지는 `options`의 `id`·`label`과 필요한 짧은 `description`·`impact`로 쓴다. `selected`는 답 기록으로만 설정되며 답변된 문항의 선택 옵션 id를 가리킨다. 승인 대상은 `blocks`의 `paragraph`(`text`), `table`(`columns`·`rows`), `fields`(`fields`) 구조로 둔다. field의 `ref`는 같은 문서 block의 `id.fieldName`을 가리킨다. blocks가 있으면 `body`를 비우고 legacy `body` 호환을 유지한다. 같은 계약·표를 body와 상세에 중복하지 않는다. `detail_blocks`는 도구가 해당 상세 출력의 소유를 확인한 경우에만 작성한다.
- 이번 작업에서 바꾸지 않는 것은 확인·질문 문서에 넣지 않는다. 꼭 필요하면 '추후' 한 줄만 쓰고, 바꾸지 않는 값을 위해 새 표·칸을 제안하지 않는다.
- 선택지(권장·대안)·남는 위험·표 밖의 설계 항목은 항목마다 한 줄에 `<주장> — <이유>`로 쓴다. 문항마다 배경·영향 단락을 따로 두지 않는다. 판단을 바꾸는 영향만 `남는 위험:`·`비용:`처럼 이름 붙인 한 줄로 두고, 근거 위치·줄 번호·조사 경위는 상세에 둔다.
- 끝난 문항은 작성자가 문서 `body`에 실제 현재 선택·유효 조건을 쓴다. 다른 절에서 명확하면 별도 결과 요약은 만들지 않는다. 답 기록 뒤 서두·명세·관련 질문의 대기 안내도 최신 답과 대조해 고친다. 상태 머리글만 맞아도 본문이 맞는 것은 아니다.
- 이번에 승인할 테이블의 컬럼·타입·키·제약과 요청·응답 구조는 정형 원본에 최신 한 벌로 둔다. 변경점만 보고 승인하게 만들지 않는다.
- 정형 원본의 body와 details에 같은 계약·표를 중복 작성하지 않는다. 상세에는 정본에 없는 기술 세부·확인 근거만 둔다. 질문 정의·답 원문·날짜·대상 개정·승인 범위는 JSON 정본·`details/history/<id>.md`·기존 개정 보관에 온전히 남긴다.
- `sfid`·`remote-config`처럼 익숙한 용어는 유지한다.
- 확인·추론·미확인을 구분하고, 조건에 따라 달라지는 결과는 조건과 함께 쓴다. 대상은 실제 이름으로 부른다.
- 각 문서는 해당 판단에 필요한 사실을 갖춘다. 다른 문서의 전체 설명은 복제하지 않고 필요한 영향과 정본 링크만 둔다. 이 일을 맡은 사람이면 이미 아는 내용은 쓰지 않는다.

작성자는 변경된 정형 원본·산문과 판단에 필요한 승인 원문·최신 답·근거·관련 규칙 절을 대조한다. 선택 양식과 예시는 필요한 부분만 적용한다. 기계 검사는 정형 구조와 상태·이력 보존을 확인하고 의미 승인 자체를 대신하지 않는다. 보고는 결과·남은 작업을, 확인 문서는 결정·승인 조건을 중심으로 쓴다. 빈 절과 미작성 양식은 공유하지 않는다. 반환에는 대조한 경로·절, 확인 결과와 남은 판단만 짧게 적는다.
확정 의미를 유지하는 산문·질문 갱신은 기계 검사와 작은 독립 의미 검토 1회로 확인한다. 검토 입력은 변경된 정형 원본·짧은 산문과 해당 승인 원문·근거·관련 절이다. 생성 Markdown·상세·전체 양식·예시는 중복 필수 입력이 아니다. 새 문서는 이전 파일이 없어도 승인 원문·근거·정형 입력을 비교 기준으로 삼을 수 있으며, 비교 기준 자체가 없으면 clean으로 판정하지 않는다. 질문·보고 문서라는 형식만으로 심층 검토에 넘기지 않는다. 중요한 계약·승인 의미 영향, 모순 또는 작은 검토로 판단할 수 없는 범위는 그 범위와 근거만 심층 검토로 반환한다. 생성 Markdown은 별도 AI 리뷰 대상으로 지정하지 않는다.
지적에는 고정 id·원인·근거 경로를 붙이고, 후속 검토에서는 변경분·직전 지적·영향받는 계약을 확인한다. 미변경 본문을 다시 열려면 실제 결함이나 원문·규칙 근거를 제시한다. 미해결·새 지적·회귀를 구분하고 이전 해소 근거를 확인한다. 같은 원인·소유·자료에 대한 수정은 묶는다. 새로 발견한 참조 누락·충돌은 코디네이터가 묶음을 맞춘 뒤 작성자와 검토자에게 함께 넘긴다.
작성자는 근거 있는 결함과 명시적 규칙 위반을 원문·현재 답에 대조해 고친 뒤 반환한다. 같은 의미의 표현·형식에 대한 Low·취향 의견은 finding이나 재파견 사유로 삼지 않는다. 관련 승인 범위를 바꾸는 수정은 다시 검토한다. 코디네이터가 나중에 문장을 고치는 방식으로 통과시키지 않는다. 기계 검사는 독립 의미 검토와 승인 판정을 대신하지 않는다.

## 새 작성자에게 넘길 자료

재작성은 변환 전 원문 보관본(선택지·설계), JSON 정본·생성 이력과 현재 문서·관련 질문에서 이미 받은 최신 답(정정·상태)을 함께 전달한다. 새 문서는 원문 보관본이 없음을 명시한다.
코디네이터는 관련 원문·승인·근거·규칙의 실제 경로와 해당 절을 확정한다. 작성자에게 양식·예시 중 필요한 부분을 지정하고, 검토자에게는 변경된 정형 원본·짧은 산문과 해당 판단 자료를 준다. 새 문서는 이전 파일 대신 명시된 승인 원문·근거·정형 입력을 비교 기준으로 삼을 수 있다. 문서 id·개정·출력·상세·이력 위치도 지정한다. 프로젝트 자료는 프로젝트 안에서 참조하며 플러그인에 복사·요약·익명화하지 않는다.

## 기존 문서를 함께 정리할 때

먼저 파일의 역할·원문 해시·답·승인 상태를 기록한다. 완료·중단 미션도 요청 범위에 포함되면 현재 유효한 결정과 적용 범위만 공유한다.
기존 질문 정의·답 원문·날짜·대상 개정·승인 범위는 정본과 이력에 그대로 보존하고, 현재 본문·상세는 현재 상태로 고쳐 쓴다.
이력으로 옮길 내용은 발행 전에 보관 위치와 누락 여부를 검토한다. `mission.md`·상태 TSV, 실행 로그·스크린샷·TSV·원문 보존본은 문체를 바꾸는 대상이 아니다.
동시에 바뀐 원문은 다시 읽어 반영한다. 확인하지 않은 과거 상태를 오늘 확인한 사실로 쓰지 않는다.
