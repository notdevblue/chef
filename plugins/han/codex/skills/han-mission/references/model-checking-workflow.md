# 동작 모델 검사 — 조사부터 환류까지

TLA+/PlusCal 모델 하나를 조사·설계·계획·구현·검증·리뷰에서 재사용한다. 별도 승인 단계나 상시 역할을 추가하지 않는다.
프로젝트별 모델·실행 자료는 해당 프로젝트의 승인된 명세·검증 자료 위치에 보존한다. 회사·고객·비공개 자료를 이 공개 플러그인으로 옮기지 않는다.

## 적용과 진입

- 컨텐츠 확인에서 상태 전이, 동시 변경, 중복 요청, 재시도, 취소·만료, 부분 실패·복구, 여러 구현 단위의 공유 동작 계약을 조사한다. 실행 순서가 정확성에 영향을 주면 핵심 프로토콜을 모델 검사 대상으로 잡는다.
- PoC 생략과 모델 검사 생략은 별개다. 기존 명세의 버그 수정도 상태·순서 계약을 바꾸면 대상이다. 작고 명백한 수정에 미션이나 모델을 억지로 만들지 않는다.
- 화면·문체·필드 정합성·단순 계산은 기존 정적 검사·단위/속성 테스트·PoC를 먼저 쓴다. 미적용이면 기존 컨텐츠 확인에 대상과 이유 한 줄만 남긴다. 별도 문서나 승인 요청을 만들지 않는다.
- 대상이면 구현 전에 모델과 검사할 규칙을 확보한다. 도구 부재·탐색 실패를 생략이나 통과로 바꾸지 않는다. 승인 범위 안에서 환경을 준비하고, 불가능하면 영향 단위를 held/미확인으로 남겨 기존 멈춤 규칙에 따라 처리한다. 무관한 작업은 계속한다.

## 단계별 사용

1. **조사** — 요구사항·기존 코드에서 상태, 이벤트, 주체, 실패·재시작 조건과 출처를 추출한다. 불명확한 제품 규칙을 모델 작성자가 임의로 결정하지 않고 기존 결정·질문 절차로 푼다.
2. **설계·PoC** — 뼈대 동의 뒤 해당 상태·데이터·통신 단계의 최종 승인 전에 핵심 모델을 검사한다. 앞 단계 미승인 계약을 확정 전제로 쓰지 않는다. PoC가 없으면 구현 계획 B 전에 검사한다. 반례를 설계에 반영하고 승인 범위 변경은 다시 승인받는다.
3. **구현 계획** — 규칙·전이를 구현 담당, 상태 변경 책임, 선행 조건, 원자적 처리 경계, 실제 테스트에 연결한다. 파일이 다르다는 이유만으로 동작 계약도 독립이라고 보지 않는다. 모델에 있는데 담당·검증이 없는 부분을 B 전에 해소한다.
4. **구현** — 담당자는 지정된 규칙·전이를 코드·테스트에 대응시키고 차이를 반환한다. 계약·원자성·환경 가정이 바뀌면 모델 담당 구현자에게 갱신을 맡긴다. 검증자가 모델을 고치지 않는다. 내부 리팩터링만으로 같은 모델을 다시 작성하지 않는다.
5. **검증** — 기존 verify 계획과 verifier로 고정 모델·설정을 실행한다. 모델 검사와 실제 구현 테스트 결과는 구분한다. 모델의 반례·대표 정상/복구 경로는 가능한 경우 실제 회귀 테스트로 옮긴다. 경로 생성이나 테스트 자동 생성이 저절로 된다고 가정하지 않는다.
6. **리뷰·통합** — 기존 독립 리뷰에서 요구사항과 모델의 대응, 구현과 모델의 대응, 단위 사이 계약을 본다. finding 원인을 모델 누락 / 구현 이탈 / 모델 밖 문제로 설명하되 기존 finding 스키마를 늘리지 않는다. 모델 통과만으로 clean을 주지 않는다. 유효한 동일 모델의 논리를 반복해서 재논증하지 않고 변경·가정·미검증 범위를 본다.
7. **수정·환류·재개** — 상태·순서 결함은 모델 누락인지 구현 이탈인지 구분해 모델 또는 회귀 테스트에 고정한다. 계약 변경이면 영향 모델·테스트를 갱신·재검사하고 관련 승인·receipt를 확인한다. 재개 시 모델 경로·설정·결과와 미확인 범위를 복원한다. C 보고·Wiki 인계에는 재현 경로와 한계를 연결한다.

모델 작성은 기존 구현 역할, 요구사항 추출은 조사 역할, 고정 실행은 검증 역할, 독립성·구현 대응 검토는 리뷰 역할이 맡는다. 브리프에는 실제 모델·설정·규칙·대응 기록 경로를 넣고 이 문서 전체를 역할마다 복사하지 않는다.

## 모델과 검사 항목

- 상태 변수, 초기 조건, 허용 전이와 주체를 정의하고 규칙에 안정된 id를 부여한다.
- **안전성**: 절대 허용하지 않는 상태(중복 부작용·유실·잘못된 권한·상충하는 종료 상태).
- **진행성**: 처리 중 영구 대기 없이 성공·실패·취소 등으로 진행하는 조건. 네트워크 복구·공정성 같은 가정을 명시하며 무제한 장애에서 완료를 보장한다고 쓰지 않는다.
- **도달 가능성**: 정상 완료와 의도한 복구 경로가 실제로 가능함을 별도 witness/탐색 근거로 확인한다. 안전성 통과만으로 정상 동작 가능성을 판단하지 않는다.
- 중복·순서 역전·동시 요청·시간 경과·부분 실패·재시작 중 해당 프로토콜에 필요한 것만 모델링한다. UI·DB·엔진 전체를 옮기지 않는다.
- 주체 수·요청 수·값 범위·큐 크기, state/action constraint, 대칭 축소 등 탐색 제한과 추상화 근거를 기록한다. 작은 유한 모델의 검사 결과를 모든 크기의 증명으로 확대하지 않는다.
- deadlock 검사는 기본 유지한다. 의도한 종료와 실제 교착을 구분하고 종료 의미를 모델로 표현한다. 실패를 없애려고 전이·속성·실패 조건을 빼거나 fairness를 근거 없이 강하게 만들지 않는다.

## 실행과 결과

공식 도구는 https://github.com/tlaplus/tlaplus 의 TLA+ tools다. Java와 승인된 `tla2tools.jar`의 실제 버전·해시·경로를 확인한다. 모델·설정과 필요한 로컬 모듈을 프로젝트 검증 입력에 포함한다. PlusCal을 사용하면 번역 결과와 원본의 일치를 확인하고 번역 도구도 식별한다.

TLC의 일반적인 호출 형태는 다음과 같다. 경로·자원 제한은 발견한 환경에 맞게 고정하며 설치·실행을 했다고 추정하지 않는다.

```text
java -cp <tla2tools.jar> tlc2.TLC -workers 1 -config <Model.cfg> <Model.tla>
```

- `-help`와 해당 버전 문서로 실제 옵션을 확인한다. 작업 cwd, 메모리·시간 상한, 상태 저장 위치를 정하고 모델/코드 입력과 생성 출력을 분리한다. simulation을 전체 도달 상태 검사로 보고하지 않는다.
- TLC 출력은 버전별로 다를 수 있다. 해당 버전에서 확인한 판독기/래퍼로 종료 코드와 완료·속성 위반·파싱/실행 오류·중단을 함께 판정한다. **종료 코드 0만으로 pass 처리하지 않는다.** 기존 실행기에 TLC 전용 판독은 내장되어 있지 않다. 실제 모델 도입 시 판독기를 프로젝트 검증 도구로 준비하고 성공·위반·파싱 오류·중단 입력으로 검증한다. 판독기가 없으면 로그를 독립 확인하되 자동 pass receipt의 근거로 쓰지 않는다.
- 결과는 검사 완료(위반 미발견) / 반례 발견 / 실행 오류 / 탐색 미완료로 구분한다. 시간·메모리 초과나 강제 종료는 통과가 아니다. 진행성·도달 가능성을 검사하지 않았다면 명시한다.
- 로그·반례/witness·검사한 속성·실제 상태 수·완료 여부를 보존한다. 초기 상태가 없거나 의도한 동작이 막힌 모델을 유효한 검증으로 보고하지 않는다.

## 근거와 재사용

기존 명세·검증 문서에 아래 항목만 추가하고 별도 정본을 중복 생성하지 않는다.

- 요구사항 출처, 모델·cfg·모듈 경로와 입력 식별자.
- 규칙 id → 모델 속성/전이 → 구현 위치·담당 → 테스트·결과의 대응. 미구현·미검증·모델 밖 항목은 명시한다.
- 환경 가정·추상화·유한 탐색 범위·제외 항목·도구 식별자.
- 실행 명령·설정·로그·반례 또는 witness·결과·미확인 한계.

모델·설정·모듈·검사 속성·범위·가정·도구가 같고 결과 근거가 유효하면 기존 검사를 재사용한다. 코드만 바뀌면 구현 대응과 영향 테스트를 다시 확인하되 변경 없는 모델 검사를 무조건 반복하지 않는다. 코드 변경이 추상화나 원자성 가정을 깨면 모델 변경으로 취급한다. 검증 입력과 모델 실행 계획을 실제 구현 테스트 계획과 분리할 수 있지만 마일스톤 완료에는 필요한 양쪽 근거를 연결한다. 현행 CLI에 여러 receipt 자동 결합 기능이 있다고 가정하지 않는다. 최종 단위 verify 계획은 필요한 모델 판독 결과와 구현 테스트를 함께 확인해야 한다.

모델 검사는 코드 정합성의 자동 증명이나 라인·브랜치 커버리지 측정이 아니다. 독립 리뷰·실제 통합 테스트·기록 감사·사람 승인은 그대로 유지한다.
