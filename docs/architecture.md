# 개발 구조와 호환성 계약

chef의 기능 구현은 `plugins/chef/chef/` Python 패키지에서 관리한다.
스킬 문서는 실행 절차를 설명하고, 기존 스킬 스크립트와 훅 파일은 패키지를 호출하는 진입점이다.
Claude·Codex·Grok·Hermes의 등록 형식과 도구 차이는 런타임 경계에 둔다.

## 디렉터리의 책임

| 위치 | 책임 |
| --- | --- |
| `plugins/chef/chef/mission/` | 미션 상태, 단위 작업, 실행 관리와 통계 |

| `plugins/chef/chef/slots/` | 슬롯 설정, 작업 흐름과 실행 |

| `tests/` | 개발용 회귀·통합·계약 검사와 가상 데이터 |
| `tools/` | 저장소 개발·구조 검사 |

## 의존성

- 일반 구현에서는 다른 스킬의 `scripts/`나 런타임 등록 디렉터리를 import하지 않는다.
- 패키지 안에서는 `chef`로 시작하는 명시적 import를 쓴다. `sys.path` 조작은 직접 실행되는 호환 진입점의 부트스트랩에만 둔다.
- 잠금·저장·경로 기능은 슬롯 CLI 같은 상위 기능에 의존하지 않는다.
- 런타임별 로그 해석과 프로세스 연결은 `runtimes/`에 둔다. 공통 기능은 이 명시적 경계를 통해 사용한다.
- 대시보드는 조회와 화면 표시만 담당한다. 승인·작업 실행·상태 변경 기능을 화면에 추가하지 않는다.
- 파일은 변경 이유가 같은 기능끼리 묶는다. 줄 수를 맞추기 위한 분할이나 모든 기능을 모으는 `utils.py`는 피한다.
- 호환 진입점은 `tools/entrypoints.json`과 `tools/generate_entrypoints.py`에서 생성한다. 등록 파일마다 기능을 따로 구현하지 않는다.

## Claude·Codex·Grok 공통 워커

세 런타임의 미션 코디네이터는 `plugins/chef/worker.py`와 `chef.workers` 공통 구현을 통해 각 역할을 라우팅한다. 이 CLI는 Python 3.11 이상에서 Windows·macOS·Linux를 지원한다. 저장소는 기본 `~/.chef/workers` 또는 `CHEF_WORKERS_HOME` 아래 로컬 JSON registry와 파일 잠금으로 작업·라우팅 이력·품질 집계를 보관한다. `worker.py --home <path>`는 사용자별 별도 registry를 지정한다.

`chef.workers.policy`는 사용자 전역 `~/.chef/config.json`과 프로젝트·요청 설정에서 `mode`, 허용 서비스 `runtimes`, 역할별 서비스 고정 `roleRouting`을 해석한다. 충돌과 형식 오류는 인증 전에 거부하며 선택된 정책·최종 허용 목록을 작업 요청에 저장한다. 후보 조회와 rate-limit 대체는 이 저장된 범위를 사용한다. 전역 설정 변경은 새 파견부터 적용하고 진행 중 작업의 범위를 바꾸지 않는다.

후보는 현재 사용 가능한 런타임 CLI·로그인, 역할 정의와 도구 역량을 충족해야 한다. 수정 후속 작업은 요청의 `previous` job key를 통해 이전 역할과 같은 런타임·세션을 이어가며, 독립 검토는 새 맥락을 선택한다. 동일 역할·조건의 독립 검증 품질 기록이 후보마다 최소 5건 있고 성공률 차이가 20%p 이상이거나 재작업률 차이가 0.5회/건 이상일 때만 품질 차이를 선택에 반영한다. 그 밖에는 진행 중 작업이 적은 후보를 고르고 동률은 순환한다. 활성 작업 수는 admission cap이 아니며 별도 동시 실행 상한을 두지 않는다.

품질 기록은 워커의 자기 보고로 만들지 않는다. `complete_unit`이 기존 검증 receipt·최신성·독립 리뷰 조건을 통과할 때만 고려한다. 출력 파일 해시가 검증 snapshot과 일치하고 결과가 성공·완료 상태이며 실제 관찰 모델·effort가 선택 경로와 일치해야 한다. 실제 실행 정보가 없거나 검증이 부족하면 품질 표본으로 세지 않는다.

외부 worker의 작업 전 probe가 rate limit을 명확히 반환하고 파일 snapshot이 그대로이며 프로세스가 정리됐을 때만 남은 후보로 자동 전환한다. 한 파견 안에서 각 후보를 한 번 시도하고, 미완료 후속 요청에는 공유 로컬 상태의 60~900초 backoff를 적용한다. 이 간격은 서비스 reset 시각·잔여 quota를 추정하지 않는다. 작업 중 오류나 이미 발생한 변경은 자동 재전달하지 않는다. 전환 결과가 current native host면 `wait`가 native handoff를 반환하고, 코디네이터가 native 역할을 직접 완료한다.

`dispatch`는 등록 프로젝트 root, 초기화된 미션·단위 계약과 현재 ACTIVE 소유권에 요청을 결부한다. native 선택은 현재 세션의 역할 도구를 사용하며, 외부 선택은 분리 supervisor가 각 런타임 CLI를 실행한다. 결과는 근거 파일·입력 snapshot과 함께 기록되며 미션 단위의 승인·완료 상태를 직접 바꾸지 않는다. `status`, `wait`, 취소, 소유권 복구와 미완료 실행 정리는 토큰으로 fence된 특정 작업에 한정된다. 설치·요청 JSON·대기·복구 절차는 [공통 워커 계약](cross-runtime-workers.md)에 있다.

작업 입력과 수정 파일은 프로젝트 상대 경로로 검사하고, 링크 경유와 미션 제어 파일 쓰기를 막는다. Claude·Codex backend는 runtime hook과 승인된 도구로 역할 작업을 가드한다. 외부 Grok은 read-only 도구로만 일하고 shell·MCP 호출 없이 JSON 변경안을 반환한다. trusted applier는 변경 전체의 지정 경로·사전 SHA-256·쓰기 권한·미션 가드를 검사한 뒤 적용 직전 재검사하여 원자적으로 기록하며, 제한된 파일 삭제도 이 경로로 처리한다. supervisor는 Windows Job Object 또는 POSIX 프로세스 그룹으로 자식 프로세스를 관리한다. backend 도구 정책과 협력형 guard는 일반 OS 파일시스템 sandbox가 아니며 임의 셸 명령·미계측 도구의 쓰기를 완전히 차단한다고 주장하지 않는다. 결과를 통합하기 전에 diff와 증거를 확인하고, `needs-inspection`은 프로세스 종료와 부분 변경 정리·증거 기록을 확인한 뒤에만 새 시도를 허용한다.

## Hermes 전용 워커

Hermes 연결은 macOS·Linux의 로컬 terminal backend를 대상으로 하며 native 세션·작업 식별자를 사용한다.
모델이 도구 인자로 넘긴 세션이나 작업 폴더를 신뢰한 실행 문맥으로 사용하지 않는다. 현재 작업의 슬롯 연결을
사용하고 프로세스 전역 `cwd`나 세션 환경변수를 변경하지 않는다. 준비와 미션 진입은 별개이며 슬롯 선택만으로 ACTIVE를 만들지 않는다.

Hermes 코디네이터는 기본적으로 현재 Hermes 프로필의 모델과 인증으로 여섯 Chef 역할을 파견한다. 선택 설정은
`workers.hermesRoles`에서 역할별 `model`과 `provider`를 지정한다. Codex와 Claude는 별도 내장 backend이며,
Codex는 등록된 역할 TOML과 `workers.codexArguments`를 사용하고 Claude는 `workers.claudeRoles`로 역할별 설정을 받는다. 명시된 backend만 선택하고 다른 인증이나
모델로 자동 대체하지 않는다. 워커 도구는 동일한 native 작업 권한을 거치며 세션·작업 소유권을 확인할 수 없으면 실행을 막는다.
Hermes native 워커는 역할별 effort를 지정하지 않고 호스트의 reasoning 설정을 따른다.
연결된 Codex TOML의 지침과 모델을 읽되 `model_reasoning_effort`는 Hermes 실행 설정으로 가져오지 않는다.

외부 워커는 명명된 `workers.attachments` 항목으로 실행한다. 각 항목은 절대 경로 실행 파일과 인자 배열만 받으며,
bridge는 제한된 JSONL 프로토콜로 역할과 도구를 요청한다. 모든 도구 호출은 현재 native 작업의 같은 가드와 권한을 통과한다.
bridge 실행 파일과 그 자식은 관리자가 신뢰해야 한다. 이 연결은 OS 파일시스템 sandbox가 아니다. Claude CLI 연결은
별도의 내장 backend가 제공한다. 공통 Claude·Codex·Grok 워커 라우터와 Hermes native의 worker 설정·실행 경로는 별개이며 서로의 설정을 상속하지 않는다. Hermes 경로는 Grok ACP를 실행하지 않는다.
작업 대기열의 새 Hermes 세션 생성, Hermes SQLite 대화 기록의 암묵적 변환, 서비스별 인증·채널 설정은 이 연결의 책임이 아니다.

## 유지하는 외부 계약

대시보드의 문서 열람은 개요의 미션·활동 수집과 분리한다. 서버 시작 때 준비한 작업 공간·미션 저장 위치를
재사용하고, 어댑터·레지스트리·로컬 설정·등록 대상 경로가 바뀌면 다시 준비한다. 문서 요청은 소속 미션을
경로에서 구하며, 전체 미션을 열거하지 않는다. 실제 경로의 포함 관계와 해당 문서의 공유 여부·해시는 매번
검사한다. 접근 설정을 다시 확인하지 못하면 이전 허용 목록으로 파일을 제공하지 않는다.

기존 스킬·훅·자동화가 호출하는 스크립트 경로, 명령 인자와 종료 코드, 훅 JSON 입출력을 유지한다.
직접 실행되는 CLI의 stdout·stderr는 운영체제 코드페이지와 무관하게 UTF-8을 사용한다.
어댑터 검색·덮어쓰기 순서, 상태 파일 이름과 형식, 승인과 세션 소유권 조건도 유지한다.
개인 어댑터나 실행 중인 미션을 구조 변경 때문에 마이그레이션하지 않는다.

파일 저장 구현을 합칠 때는 인코딩, 줄바꿈, 원자적 교체, 임시 파일 정리와 동기화 보장을 구분한다.
기존 text writer는 프로세스 umask가 적용되는 생성 모드를 유지하고, mkstemp 기반 writer는 제한된 생성 모드를 유지한다.
잠금은 기존 영구 gate와 PID marker 계약을 유지한다. 살아 있는 소유자의 잠금을 시간만으로 회수하지 않는다.
gate는 빈 파일에서도 잠글 수 있다. 잠그기 전에 초기 바이트를 쓰면 다른 Windows 소유자의 잠금과 충돌하므로 쓰지 않는다.

검증 결과 재사용에는 분리된 구현 파일도 식별해야 한다. 구현이 바뀌면 과거 결과를 새 실행의 증거로 재사용하지 않는다.
기존 결과는 이력으로 읽을 수 있으며, 코드 변경에 따른 보수적인 재검증은 정상 동작이다.
새 구현 지문은 설치 절대 경로와 무관하게 패키지의 모든 Python 파일 이름과 내용으로 계산한다.
상태·결과 JSON의 스키마는 유지한다.
Windows의 일시적인 읽기 공유 충돌(오류 5·32·33)은 같은 완성된 임시 파일로 최대 0.5초 동안 교체를 재시도한다.
호출자가 잡은 gate를 유지하며, 충돌이 계속되면 기존 목적지 파일을 삭제하지 않고 실패한다.

## 운영체제 경계

실제 파일 경로는 실행 OS의 규칙으로 해석한다. POSIX 파일명의 리터럴 역슬래시는 경로 구분자로
바꾸지 않는다. 존재하는 경로의 동일성은 파일시스템의 실제 식별자로 비교하고, 포함 관계도 실제
부모 디렉터리를 확인한다. Linux 경로 전체를 소문자화하지 않으며, 슬롯 자체의 링크 거부와
동일한 작업 공간의 별칭 판정은 별개로 유지한다.

검증 프로세스의 argv는 실행 파일과 인자 배열로 검사한다. 일반 인자의 셸 기호는 데이터이며,
명시적으로 셸을 호출할 때만 명령 문자열을 셸 문법으로 분석한다. 검증 가드는 `guard.argv(argv, cwd)`를
제공하고 기존 문자열 콜백도 호환한다. 실행 시 실제 cwd와 환경변수 PWD를 일치시킨다.
이 계약은 Claude·Codex·Grok·Hermes가 사용하는 공유 검증 경로에 적용한다.

검증 실행과 지원되는 리뷰 명령은 계획 입력 경로의 cooperative lease를 등록하고, 공유 쓰기 가드는 지원되는 파일 도구·알려진
리터럴 쓰기 대상과 Rename 경로의 사용 직전에 충돌을 검사한다. 경로 별칭 목록은 lease 등록 때 계산한다. lease 저장소와 경로
인덱스는 중첩 깊이·크기에 제한이 있으며 상태를 안전하게 확인할 수 없거나 한도를 넘으면 fail closed한다. 이는 OS 파일 잠금이나
임의 프로세스 쓰기 차단이 아니므로, 해석할 수 없는 동적 shell 경로·미계측 쓰기·분리된 후손 프로세스는 보장하지 않으며 미계측
변경은 실행 뒤 입력 hash로 감지한다. 같은 단위의 검증·계약 변경·완료 처리는 단위 실행 gate로 직렬화한다.

슬롯 런처는 런타임 CLI 인자와 터미널 백엔드를 분리한다. GUI가 없는 Hermes는 현재 작업의
`chef_slot`을 사용한다. 다른 런타임의 터미널 실행은 사용 가능한 백엔드를 먼저 확인한다.
Python 실행 환경은 자식 프로세스에만 연결하며 시스템 Python 별칭이나 부모 PATH를 바꾸지 않는다.
POSIX의 개인 캐시 실행기는 원래 인터프리터 경로를 exec하여 가상환경을 유지한다.

0.6부터 OS별 어댑터 설정층과 `runtimes.claude`를 지원한다. 기존에 무시되던 Claude 설정층을
개인 어댑터에 작성했다면 이제 적용되므로 업데이트 전에 확인한다. 정확한 병합 순서는
[어댑터 계약](../plugins/chef/skills/mission/references/adapter-schema.md)을 따른다.

## 변경과 검증 순서

1. 변경 전 전체 회귀 검사를 실행해 기준 결과를 확보한다.
2. 테스트를 배포 트리 밖으로 옮기고, 공통 패키지와 기존 경로의 진입점을 연결한다.
3. 기반 기능을 추출한 뒤 슬롯·미션·검증·대시보드를 책임별로 분리한다.
4. 테스트의 동작·입력·검증 조건을 보존하며 새 소유 모듈로 import와 패치 위치를 갱신한다.
5. 구조 검사, 전체 회귀 검사, 임의 작업 폴더와 복사된 설치 트리에서의 명령·훅 검사를 수행한다.
6. Windows/macOS/Linux와 Python 3.11·3.13의 CI 결과를 확인한다. 로컬 결과와 미실행 환경을 구분한다.
7. 공개 경계 점검과 저장소 완료 절차에 따라 배포·설치본·실행 중 대시보드를 확인한다.

테스트는 정답이 아닌 현재 구현을 복제하지 않는다. 기존 테스트 삭제로 실패를 숨기지 않고,
위험한 동작인 상태 변경·동시 실행·경로 접근·검증 재사용을 실제 관찰 결과로 확인한다.
구조 검사는 테스트 혼입, 구현의 경로 조작과 등록 디렉터리 의존이 다시 생기면 실패해야 한다.

Hermes의 미션 상태 변경은 `chef_mission` 도구 handler가 담당한다. 사전 훅은 검증만 하며 shell marker는 native bridge에서 거부한다. `contracts.py`는 명시된 외부 읽기 파일과 역할 지침·모델 정책의 해시를 확인한다. 다른 런타임의 기존 marker와 명령·훅 경로는 유지한다.
